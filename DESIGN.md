# Unepic Trainer design

The standalone trainer is implemented. The user has verified the basic player combat cycle in Unepic; `README.md` and `runtime-notes/` identify the remaining checks. Project root: `/home/af/devel/games/unepic`.

The target is the user's Linux single-player Unepic installation. The application provides player/minion health, healing, reversible damage protection, maximum minion ENERGY, extra skill points, immediate campaign level-up, gold, Unepic Credits, Kill Points and manual saving through a desktop interface.

## Approach

Python 3 implements the application; PySide6/Qt Widgets implements the interface. PySide6 6.11.2 is available on the development machine. A separate backend controls GDB and process memory. GDB operations run in a worker thread; Qt widgets remain in the main thread. Periodic displays use a read-only `/proc/PID/mem` view without stop/resume or GDB round trips. Process identity is checked around each view, character/room pointers are compared around the sample, and a transient inconsistent sample is retried once. Live data never authorizes writes. If live access is denied, only explicit Refresh/connect/action requests may use stopped snapshots; periodic polling never falls back to interruption.

The damage trampoline is x86-64 machine code generated by Python. PINCE can assist runtime investigation but must be used separately from the trainer when attaching to a process. A PINCE table is not the distribution format.

scanmem/libscanmem and libmemscan are separate projects. They may help discover future values or addresses but are not dependencies of this version. If scanning becomes an application feature, add a separate adapter after checking its API, integration and distribution requirements.

## Interface

A compact dark desktop window provides:

- Process selection, refresh, connect and disconnect.
- Connection and character availability status.
- Current/max HP and a health bar.
- God mode toggle, Full heal and Save game actions.
- Level and XP displays, points to distribute with +1/+10/+100 actions, and immediate Level up.
- Gold +100/+1000/+10000 through native campaign inventory award.
- Unepic Credits +100/+1000/+10000 through the saved campaign source counter.
- Kill Points (KP) bar with +1/+10/+100, capped at the native 5 KP maximum and requiring the existing unlock.
- Two columns: Player on the left and Minion on the right.
- Plain-text errors and the ability to disable an active hook even if the character becomes unavailable.
- Save directory selection when automatic discovery cannot find saves.

There is no overlay. Updates must not block the interface. All interface text, application messages and publishable documents use English. User conversation remains in Bulgarian. Preserve original strings and bytes in retained artifact evidence.

The minion section displays aggregate HP and ENERGY for living owned type-4 pets in the current room. Heal minion, Minion god mode and Lock energy at maximum are independent controls. Ownership is resolved dynamically; recall/death is excluded. With several pets, controls apply to all qualifying pets. ENERGY fills to its current cap and remains there through three spending/regeneration hooks. Findings and unresolved game checks are in `runtime-notes/minion.md`.

The two HP trampolines share player/minion enable bits in one mapped page. A separate page holds the three ENERGY trampolines. Disabling one HP toggle leaves the other active; both original HP instructions are restored when neither is selected. All registers, flags and the SysV red zone are preserved, including the complete XMM0 register used for energy conversion. Normal disconnect restores both sets of instructions before detaching.

Window closing and terminal SIGINT/SIGTERM request the same worker cleanup. Explicit application shutdown occurs only after verified detach and thread completion, regardless of Qt's implicit last-window policy. A main-thread timer services Python signals; it does not read or write game memory. Failed recovery keeps the window and worker available for retry.

## Current behavior

1. Discover the process and validate executable SHA-256 and process identity.
2. Read the current entity pointer, HP, integrity flags and protected progression values.
3. Reject invalid runtime data before enabling memory changes.
4. Back up discovered saves before the first change.
5. Full heal restores current HP to the current calculated maximum.
6. God mode conditionally skips the known direct and periodic damage stores for the selected player's current body.
7. Disabling or normal disconnect restores original instructions; expired process identities cannot be reused.

Supported executable: Linux x86-64 `unepic64s`, SHA-256 `62c04002b98eee3f33d0f8c27030b1f5ea23d3ede56d62af9da6b1436a583962`.

| Field or function | Location |
|---|---|
| First character | `0x0142d620` |
| Body pointer | character `+0x197b8`, absolute slot `0x01446dd8` |
| Maximum HP | body `+0x4e8`, int32 |
| Current HP | body `+0x4ec`, float32 |
| Shared damage function | `0x004caed0` |
| Direct HP damage store | `0x004caf49`, MOVSS from XMM2 |
| Periodic damage function | `0x004cb250` |
| Periodic HP damage store | `0x004cb2ad`, MOVSS from XMM3 |

The user has verified the basic HP and damage behavior for this build. The damage function is shared with other objects, so the hook must be conditional. The second store was added after reports of burning and poison bypassing protection. Both stores pass controlled tests; game verification of the update is pending. Details: [periodic damage](runtime-notes/damage-over-time.md). Coverage of traps, scripted deaths and direct HP-zero paths remains unknown.

## Protected values

XP, XP threshold, level and available skill points have primary and mirror XOR copies. External changes would require both copies to be updated while the checker cannot run, or through a verified game operation. The authorized progression extension calls native setters and XP/level-up routines from a one-shot hook on the game's own character-update thread. It validates campaign mode, the living body, room, integrity flags, all four XOR pairs, balances and original function bytes. The native dispatch repeats context checks and atomically claims a request. Invalid or stale requests are cancelled; repeated updates cannot replay them. Native calls preserve GPRs, flags, the red zone and x87/MMX/MXCSR/XMM state. The update entry is restored on disconnect; its mapping remains allocated so a thread already executing there can return safely. Details: [progression design and evidence](runtime-notes/progression.md).

An integrity violation triggers damage and resets progression and inventory. Preventing that damage alone does not prevent the other penalties. Inventory and skill plausibility checks also exist.

## Verification

- Owned-process backend tests for reads, writes, interrupt/resume, allocation and restoration.
- Executable hash, PID reuse and executable replacement checks.
- Simulated interface checks, shutdown recovery and visual inspection.
- User-performed game checks with save backups: HP, healing, player/enemy damage and enable/disable behavior.
- Separate recording of untested transitions, save/load, disconnect and lethal scenarios.

Static analysis is not runtime evidence. Host terminal results and sandbox skips must be recorded separately.

## Filesystem constraints

Keep code, REA exports, Ghidra projects, logs, fixtures, builds and backups inside the project. The Steam installation `/home/af/.local/share/Steam/steamapps/common/Unepic` is read-only. Do not edit executables, launchers, assets or saves there. The trainer changes only the authorized running process memory.

If a tool writes beside its input, work on a project-local copy. The original `rea-analysis/` directory was relocated into this project and its hashes checked; do not recreate it in the game installation.

## Distribution

The product is a standalone desktop application with build checks and startup instructions. A wheel has been built and installed offline in a project venv using system dependencies. A dependency-isolated installation, a second Linux environment and AppImage portability remain unverified. Do not bundle game executables, raw saves or analysis evidence in the trainer package.

XP multipliers and inventory changes other than Gold and Unepic Credits remain outside the current scope. Authorized gold uses a validated one-shot native award with all inventory XOR pairs and capacity checked. Manual saving queues the normal game request in the current slot and retains difficulty. The game owns serialization, storage, restrictions and confirmation. Pending character changes and saves are serialized. Design, evidence and host checks: [saving and gold](runtime-notes/saving-and-gold.md).

Unepic Credits differ from Gold: normal updates set their protected item quantity to earned challenge scores minus the saved per-hero counter at +0x170. A one-shot request subtracts the amount from that signed source counter after runtime context/inventory/score/overflow checks; the normal update then rebuilds the item. Negative source counters intentionally represent added credits. The writer/loader preserve the raw counter. Controlled persistence checks do not establish actual Unepic save/load behavior. Details: [credits](runtime-notes/credits.md).

Kill Points use the plain hero counter at +0x174 and unlock flag at +0x178. Five steps equal one displayed KP, with 25 steps maximum. One-shot action 5 adds five steps per requested KP, clamps to 25 and sets the normal character update flag at +0x234. It repeats campaign, living body, room, integrity, active-hero and unlocked/counter/amount checks and preserves CPU state. It does not unlock KP, change cost rules or write the HUD copy. Live display reads reuse the existing character block. Actual-game spending and persistence remain unverified. Details: [Kill Points](runtime-notes/kill-points.md).
